# 公共评分标准与反馈模板

## 评分原则

- 每个基础维度使用 1-10 分，只引用本场面试中的回答、代码或项目证据。
- 身份映射：`daily_intern` 和 `summer_intern` 均使用“实习”权重，`campus` 使用“应届”权重，`social_1_3` 使用“社招”权重。身份影响评分标准深度，但不改变映射。
- 单语言和混合语言使用不同公式与权重表。混合语言的主语言、次语言是两个独立维度，不能先合成“语言专项能力”再计分。
- 每条评分证据必须有唯一 `evidence_id` 和一个 `score_dimension`。同一 `evidence_id` 不得重复计分；同一回答拆分 facets 时，每个 facet 使用不同 ID 且只进入一个维度。
- 通用系统设计题的每个 facet 只能计入 `common_backend` 或 `system_engineering`。编码题可把语言正确性和工程 facets 分别计入实际语言与系统设计/工程，但不能把整个回答重复计分。
- 未考察维度不打分，不填 `0`，也不进入分子或分母；报告中明确标记“未考察”。
- 提前结束、跳题或读取失败时，按已考察维度的原始权重重新归一化。归一化只避免缺失项扣分，不代表完整面试能力。
- AI 能力和 JD 匹配是附加评价，不进入基础综合分；没有实际考察时不输出分数。

## 身份权重

### 单语言权重

| 身份 | 项目经验 | 通用后端 | 主语言 | 系统设计/工程 | 思维表达 | 总计 |
|---|---:|---:|---:|---:|---:|---:|
| 实习 | 25% | 20% | 20% | 10% | 25% | 100% |
| 应届 | 25% | 20% | 25% | 15% | 15% | 100% |
| 社招 | 30% | 15% | 25% | 20% | 10% | 100% |

### 混合语言权重

混合模式默认把语言预算按主语言 70%、次语言 30% 独立拆分。若简历显示实际投入明显不同，可在语言阶段开始前调整主次拆分，但必须保持该身份的语言总预算不变、全维度总计 100%，并记录调整理由；不能在看到面试表现后改权重。评分必须使用会话中已冻结的 `language_weight_split`，不能重新采用默认值。

| 身份 | 项目经验 | 通用后端 | 主语言 | 次语言 | 系统设计/工程 | 思维表达 | 总计 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 实习 | 25% | 20% | 14% | 6% | 10% | 25% | 100% |
| 应届 | 25% | 20% | 17.5% | 7.5% | 15% | 15% | 100% |
| 社招 | 30% | 15% | 17.5% | 7.5% | 20% | 10% | 100% |

表中主/次列是默认 70/30。若冻结值已调整，先取该身份的语言总预算（实习 20%、应届 25%、社招 25%），再计算：

```text
主语言权重 = 语言总预算 × language_weight_split.primary / 100
次语言权重 = 语言总预算 × language_weight_split.secondary / 100
```

冻结 split 的 primary 与 secondary 必须合计 100；项目、通用后端、系统设计/工程和思维表达权重不变，因此总权重仍为 100%。

## 综合评分计算

```text
单语言：
单语言综合分 = 项目经验 + 通用后端 + 主语言 + 系统设计/工程 + 思维表达

混合语言：
混合语言综合分 = 项目经验 + 通用后端 + 主语言 + 次语言 + 系统设计/工程 + 思维表达
```

上式中的每一项是 `维度分 × 身份权重`。完整考察时：

```text
综合分 = Σ(维度分 × 身份权重)
```

存在未考察维度时：

```text
阶段性综合分 = Σ(已考察维度分 × 原始权重) ÷ Σ(已考察维度原始权重)
```

若 `Σ(已考察维度原始权重) = 0`，不计算综合分、不输出 `0`，只输出“证据不足，无法评分”以及未考察范围。

最终分数保留 1 位小数。报告同时列出各维度原始分、权重、证据和未考察项；阶段性综合分必须标记“仅覆盖已考察范围”。

## 维度评分锚点

### 项目经验

| 分数 | 证据要求 |
|---|---|
| 9-10 | 能说明业务目标、个人职责、关键实现、量化结果、失败案例和复盘；社招还应体现生产决策 |
| 7-8 | 项目真实完整，能说清自己的贡献、难点与主要取舍 |
| 5-6 | 能描述项目和职责，但技术深度、规模数据或验证证据有限 |
| 3-4 | 大量使用团队或框架术语，无法说明个人实现与结果 |
| 1-2 | 无法形成可验证的项目描述 |

### 通用后端

| 分数 | 证据要求 |
|---|---|
| 9-10 | 机制准确，能推导选型、失败边界、容量与验证方法 |
| 7-8 | 核心原理正确，能处理常见边界并解释主要取舍 |
| 5-6 | 概念和用途基本正确，深入追问时证据有限 |
| 3-4 | 多个关键概念混淆，需要提示才能继续 |
| 1-2 | 关键基础无法作答 |

### 主语言

评价主语言的语义、资源或内存模型、并发、标准库、运行时、工具链、编码和排障。混合模式仍要求独立证据，不因次语言表现修正主语言分。

| 分数 | 证据要求 |
|---|---|
| 9-10 | 能从规范/运行时到工程验证完整解释，并写出边界可靠的代码 |
| 7-8 | 核心机制正确，常用库和编码熟练，能说明主要版本边界 |
| 5-6 | 可完成常规实现，但底层原理、错误处理或排障深度有限 |
| 3-4 | 关键语义混淆，代码存在明显正确性或资源风险 |
| 1-2 | 无法完成基础语言任务 |

### 次语言

仅混合语言且实际考察时评分。重点评价候选人是否理解它与主语言在语义、资源管理、并发、工具链和适用边界上的差异；不得把主语言分数复制过来。

| 分数 | 证据要求 |
|---|---|
| 9-10 | 能独立完成实现，并准确比较两门语言的运行时与工程取舍 |
| 7-8 | 常用语法和标准库熟练，能解释主要差异并处理常见边界 |
| 5-6 | 能完成基础实现，但专项原理或工程经验有限 |
| 3-4 | 仅有零散使用经验，多处关键语义不准确 |
| 1-2 | 无法用次语言完成基本任务 |

单语言面试中的次语言标记“未考察”，不能显示 `0` 分。

### 系统设计/工程

| 分数 | 证据要求 |
|---|---|
| 9-10 | 能从需求、容量、不变量、架构、故障模式、可观测性到验证闭环完成设计 |
| 7-8 | 设计结构完整，能说明核心取舍、故障处理和上线验证 |
| 5-6 | 能给出可行主流程，但容量、一致性或工程验证不完整 |
| 3-4 | 只罗列组件，无法解释数据流、边界和故障行为 |
| 1-2 | 无法形成可执行设计或排障路径 |

### 思维表达

| 分数 | 证据要求 |
|---|---|
| 9-10 | 先澄清假设，再结构化推导；术语准确，能主动修正错误并解释依据 |
| 7-8 | 逻辑连贯、表达清晰，能在追问下补齐主要论证 |
| 5-6 | 基本可理解，但存在跳步、假设未声明或术语不稳定 |
| 3-4 | 前后矛盾，需要多次追问才能识别结论 |
| 1-2 | 无法形成有效沟通 |

## 各风格反馈措辞示例

同一份面试结果，六种风格只改变措辞，不改变评分事实。以下使用通用后端证据不足、项目量化不足的场景，不绑定具体语言：

```text
项目经验 6.0，通用后端 5.0，主语言 6.0，
系统设计/工程 5.0，思维表达 6.0。
```

### 严厉拷打型

```
项目和基础达到最低要求，但证据不足。你没有给出容量、延迟和故障数据，
系统设计也没有说明失败边界。技术差距是：
1. 补一份项目容量与性能基线。
2. 用一次故障演练证明排查路径。
3. 针对主语言补齐运行时或资源管理证据。
```

### 温和鼓励型

```
你的核心概念方向基本正确，项目职责也能说明。下一步建议补充容量、延迟和故障证据，
再选择一个主语言机制深入到运行时或资源边界。这样能把当前“会使用”的证据提升为“能解释和验证”。
```

### 专业高效型

```
【结论】基础可用；项目证据和系统设计边界不足。
【证据】核心概念正确；未给出容量、延迟、故障时间线和验证方法。
【行动】1. 建立压测基线。2. 复盘一次故障。3. 深挖一个主语言运行时机制。
```

### 深挖学术型

```
你的回答能描述“是什么”，但对假设、边界和反例论证不足。
建议选择本场一个核心机制，补全设计目标、替代方案、复杂度或资源代价，以及如何用实验验证。
```

### 工程实践型

```
项目主流程能说明，但缺少生产证据：基线 QPS、P95/P99、资源水位、错误率和故障时间线。
建议先对核心接口做压测，再用监控、日志和 profile 复盘瓶颈，记录改动前后数据。
```

### 综合平衡型

```
你的基础和表达达到当前身份的基本要求。主要提升点是项目量化、系统故障边界和主语言机制深度。
建议先补一份可复现的性能报告，再针对本场最薄弱的机制做源码或运行时验证。
```

## D. 目标岗位匹配分析（可选附录）

`jd_provided=true` 且存在面试证据时，可在标准评估报告后输出此分析。仅提供 JD 且已有面试证据时，也可输出技术匹配和经验匹配；只有 `resume_provided=true` 时才输出“面试表现 vs 简历描述”和简历优化。

### 覆盖率与表现分离

先把 JD 拆为可独立验证的要求，并标记 `must-have` 或 `nice-to-have`。只统计与目标岗位及本场允许考察范围相关、能够通过技术回答、代码或项目证据判断的要求；纯公司宣传、福利、地点等不进入分母。

```text
JD 覆盖率 = 已验证 JD 要求数 ÷ 可评估 JD 要求总数
```

“已验证”表示有足够的对应证据可将该要求判定为“匹配”或“缺口”；只提到关键词、使用其他维度推断或尚未提问都属于“待验证”。覆盖率回答“本场验证了多少 JD”，已验证项表现回答“验证到的能力有多强”，两者必须分别报告。

输出门禁：

- JD 覆盖率低于 80% 时，不得输出整体星级或 `X/5`，整体结论固定为“证据不足 / 待验证”。
- 任何 must-have 仍未验证时，不得输出整体星级或 `X/5`，即使已验证项目表现很强。
- 只有 JD 覆盖率至少 80%、全部 must-have 已验证时，才可根据已验证项表现输出整体星级和 `X/5`。
- 5/5 还要求 JD 覆盖率达到 90%、全部 must-have 有强证据且不存在已证实的关键缺口。不得把少量强回答归一化为“高度匹配”。
- 门禁未通过时仍要逐项列出匹配、缺口和待验证要求，但不能用已验证项平均分代替整体岗位匹配。

证据判定：

- 技术栈匹配只使用语言、`common_backend`、`system_engineering` 或其他明确技术证据。没有对应技术证据的 JD 要求标记 `⚠️ 待验证`，不能推断为缺口。
- 项目经验没有相关证据时标记 `⚠️ 待验证` 或省略。只有候选人明确否认相关经验，或回答证实能力不足时，才能标记 `❌ 缺口`。
- 不得从未问过推断缺乏。每个子部分只引用其对应 `score_dimension` 或 facet 的 `evidence_id`。
- `⚠️ 待验证` 不按缺口扣减，但会降低 JD 覆盖率；不能通过忽略待验证项抬高整体等级。

```
──────────────────────────────────────────
     📋 目标岗位匹配分析
──────────────────────────────────────────

【目标岗位】[JD 中的岗位名称 / 公司名称]
【JD 覆盖率】[已验证数] / [可评估总数] = [百分比]
【Must-have 状态】全部已验证 / 仍有 [N] 项待验证
```

### 匹配度评级标准

下表只在 JD 覆盖率至少 80% 且全部 must-have 已验证后使用。评级依据是已验证项的证据强度和已证实缺口，不重新归一化未验证要求。

| 星级 | 含义 | 说明 |
|------|------|------|
| ★★★★★（5/5） | 高度匹配 | 覆盖率至少 90%，全部 must-have 有强证据，无已证实关键缺口，其他已验证项表现优异 |
| ★★★★☆（4/5） | 较好匹配 | 主要要求匹配，有 1-2 个小缺口但可短期补齐 |
| ★★★☆☆（3/5） | 基本匹配 | 核心技能匹配但有明显缺口，需要重点准备 |
| ★★☆☆☆（2/5） | 匹配不足 | 多个关键要求不满足，需要较长时间准备 |
| ★☆☆☆☆（1/5） | 严重不匹配 | JD 要求与当前能力差距很大，建议调整目标岗位 |

#### 各风格匹配分析措辞示例

**严厉拷打型：**

```
整体匹配度 ★★☆☆☆（2/5）。当前证据不满足岗位要求：JD 要求微服务经验和
缓存实战，但本场回答没有给出准确的机制与实践证据。
建议：
1. 完成一个可运行的微服务项目并记录故障与验证证据
2. 补齐缓存穿透、击穿、雪崩的机制和边界
3. 完成一次同岗位模拟复测后重新评估差距
```

**温和鼓励型：**

```
证据不足 / 待验证：本场只验证了主语言基础，JD 覆盖率为 60%，
且微服务这一 must-have 尚未验证，因此不输出整体星级。已验证的主语言
基础与岗位要求吻合；下一轮应优先验证微服务经验和数据库调优能力，再评估整体匹配。
```
