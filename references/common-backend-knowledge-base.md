## 1. MySQL

### 基础问题与答案要点

**索引与执行计划**

- **B+ Tree 为什么适合数据库索引？** — 多路结构降低树高和随机 I/O 次数；非叶子页主要保存导航键；叶子页按键有序，适合点查、范围扫描和排序。比较索引结构时应同时考虑页大小、访问模式、更新成本和存储开销
- **聚簇索引、二级索引、覆盖与回表是什么关系？** — InnoDB 聚簇索引的叶子页保存完整行；二级索引叶子项保存索引列和主键。查询列都能从所选索引取得时形成覆盖索引；否则通常根据二级索引中的主键再次访问聚簇索引，即回表。是否覆盖以实际查询列和执行计划为准
- **联合索引如何设计？** — 先从真实查询模式、过滤选择性、排序分组和覆盖需求出发。最左前缀描述可利用的有序前缀，但范围条件后的列是否可参与过滤或排序要以具体执行计划为准，不能背成绝对的“遇到范围就全部失效”
- **Index Condition Pushdown（ICP）解决什么问题？** — 存储引擎扫描二级索引时，先用可下推的索引列条件过滤，再决定是否回表，减少不必要的聚簇索引访问。它不等于覆盖索引，也不是所有访问类型、条件和存储引擎都适用；需通过目标 MySQL 版本的 `EXPLAIN`/执行统计确认
- **EXPLAIN 重点看什么？** — `type`/access type 反映访问方式，`possible_keys` 与 `key` 区分候选和实际索引，`key_len` 帮助判断使用的索引前缀，`rows` 与 `filtered` 是优化器估算，`Extra`/执行计划节点显示覆盖、ICP、排序、临时表等线索。MySQL 8.0.18+ 可在适用场景用 `EXPLAIN ANALYZE` 对比实际行数和耗时；任何单一字段都不能独立证明性能
- **常见 JOIN 执行方式如何理解？** — Nested Loop 是关系连接的基础执行思路，优化器可结合索引形成高效的索引嵌套循环；Hash Join 适合可哈希的等值连接，但可用性与选择规则取决于 MySQL 版本、执行计划和数据规模。驱动顺序、输入基数、连接条件、索引、内存与溢写共同决定成本，不能把“小表驱动大表”当作脱离计划的固定口诀

**事务、MVCC 与锁**

- **ACID 分别解决什么问题？** — 原子性保证事务内操作整体提交或回滚；一致性是业务约束在事务前后成立；隔离性约束并发事务相互影响；持久性保证提交结果在故障后可恢复
- **四种隔离级别如何权衡？** — 隔离越强，异常现象越少，但并发与等待成本通常越高。MySQL InnoDB 默认 `REPEATABLE READ`，实际行为还取决于快照读、当前读、锁范围和具体版本
- **MVCC 的核心机制是什么？** — 行版本信息、undo log 版本链和 ReadView 共同判断某个版本对当前事务是否可见。`READ COMMITTED` 通常每次一致性读创建新 ReadView，`REPEATABLE READ` 通常复用事务中的一致性视图
- **记录锁、间隙锁和 Next-Key Lock 有什么区别？** — 记录锁锁定索引记录；间隙锁约束索引区间插入；Next-Key Lock 组合记录与间隙范围。锁定范围由访问路径和查询条件决定，不应把“未命中索引”简单等同为固定的表锁
- **数据库死锁如何处理？** — 数据库检测等待图中的环并回滚一个事务。应用需记录死锁错误、控制重试边界；设计上统一资源访问顺序、缩短事务、减少无关锁范围，并用死锁日志确认真实冲突语句

**SQL、复制与扩展**

- **慢 SQL 如何定位？** — 先用慢查询日志或数据库观测平台确认频率、分位延迟和扫描量，再看执行计划、索引统计、锁等待、返回行数和应用调用方式。优化后必须对比同等数据与负载
- **一条 SQL 的主要执行阶段是什么？** — 连接与权限检查、解析、优化器生成计划、执行器调用存储引擎、返回结果。性能问题可能出现在排队、锁等待、执行、网络传输或客户端消费，不只在 SQL 文本
- **主从复制的基本链路是什么？** — 主库记录 binlog，从库拉取并重放。读写分离能扩展读能力，但会引入复制延迟、读己之写和故障切换一致性问题
- **什么时候考虑分库分表？** — 单实例容量、吞吐、维护窗口或故障域已成为经测量的瓶颈，且索引、SQL、归档、读扩展等低成本措施不足时再考虑。分片会引入路由、跨分片事务、聚合查询和扩容迁移成本

### 连续追问

1. 这条查询的过滤、排序和返回列分别是什么，当前索引为什么能或不能覆盖？
2. `Using index` 与 `Using index condition` 分别说明什么，后者为什么仍可能回表？
3. `rows` 估算与 `EXPLAIN ANALYZE` 实际行数差异很大时，应检查哪些统计信息和数据分布？
4. JOIN 算法或驱动顺序变化后，循环次数、随机 I/O、内存和临时结果如何变化？
5. 如果加索引改善读延迟，写放大、锁竞争、磁盘和复制延迟增加多少？
6. 主从延迟时如何保证用户刚写入的数据可读，业务允许的陈旧窗口是多少？
7. 方案上线后观察哪些分位延迟、扫描行数、锁等待和错误率，回滚阈值是什么？

### 常见误区

- 用固定数据量阈值决定分库分表，不看行宽、访问模式、硬件、SLA 和增长速度
- 只看 `key` 字段就断言索引有效，不检查扫描行数、回表、排序和实际耗时
- 把 ICP 当成覆盖索引，或看到 `Using index condition` 就断言没有回表
- 只背 JOIN 算法名称，不结合目标版本的实际计划、输入基数和内存约束
- 把 `REPEATABLE READ` 概括成“绝对不会幻读”，忽略快照读与当前读差异
- 用 `SELECT *` 和超大分页制造无谓 I/O，再试图仅靠增加索引解决
- 遇到死锁只增加重试次数，不修正事务边界、访问顺序和幂等性

## 2. Redis

### 基础问题与答案要点

**数据结构、持久化与高可用**

- **Redis 延迟低的主要原因是什么？** — 热数据位于内存，核心命令路径短，采用事件驱动 I/O 和针对场景优化的数据结构。Redis 6 引入可配置的 I/O threads，用于分担部分 socket 读写和协议处理；经典 Redis 6 命令执行仍主要由主线程串行完成。后续版本持续演进多线程实现，面试结论必须限定目标版本、配置和具体命令
- **SDS 解决了什么问题？** — Redis 字符串对象的底层字符串表示使用 SDS（Simple Dynamic String），显式保存长度和容量，支持二进制安全、常数时间获取长度，并降低反复追加时的重新分配次数。SDS 结构布局会随版本演进，不应把某组内部字段或 header 类型当作稳定公开 API
- **逻辑数据类型、内部编码和复杂度如何区分？** — String、Hash、List、Set、Sorted Set 等是对外逻辑类型，内部可根据元素数量、大小和版本使用 int、raw/embstr、listpack、hashtable、skiplist 等不同 encoding，并在阈值触发时转换。命令复杂度取决于命令语义、元素数量、返回结果规模和实际 encoding；不能笼统说“Redis 所有操作都是 O(1)”
- **常用数据类型如何选？** — String 适合标量、计数和位操作；Hash 适合字段集合；List 适合双端序列；Set 适合集合关系；Sorted Set 适合按 score 排序和范围查询。选型同时考虑所需命令复杂度、内部 encoding 转换、单 key 大小、网络返回量和内存开销
- **RDB 后台快照如何工作？** — `BGSAVE` 通常通过 `fork` 创建子进程生成快照，父子进程依赖操作系统 Copy-on-Write 共享初始内存页。写流量会触发页面复制，因此大数据集下要观察 fork 延迟、额外内存、磁盘吞吐和容器内存限制；具体实现与平台能力需按版本核对
- **AOF 的 fsync 策略如何权衡？** — `appendfsync always` 在追加后频繁同步，持久性更强但延迟成本高；`everysec` 周期同步，在故障窗口与吞吐间折中；`no` 交给操作系统安排同步。数据损失窗口和性能还受文件系统、磁盘、批处理与 Redis 版本影响，不能只背固定时长
- **混合持久化是什么？** — 支持该能力的 Redis 版本可在 AOF 重写结果中使用 RDB 格式的基线加后续 AOF 增量，兼顾恢复速度和增量记录。启用方式、文件组织和兼容性随版本变化，恢复演练应使用与生产一致的版本和配置
- **Sentinel 与 Cluster 解决什么问题？** — Sentinel 监控非分片主从部署并协助故障转移和服务发现，不承担数据分片；Redis Cluster 将 keyspace 映射到固定的 16384 个 hash slots，节点负责其中一部分槽并支持槽迁移与故障转移。两者都不能消除异步复制窗口中的数据丢失风险，也不能自动解决 hot key
- **过期 key 如何删除？** — Redis 组合惰性过期与主动过期：访问 key 时检查 TTL，同时后台周期性抽样并清理过期 key。抽样算法、时间预算和配置随版本演进，因此不能写成每秒固定次数或保证到期瞬间释放内存
- **达到 maxmemory 后如何淘汰？** — `maxmemory-policy` 决定从全部 key 或仅带 TTL 的 key 中按近似 LRU、近似 LFU、随机、剩余 TTL 等策略选择，或使用 `noeviction` 拒绝会增加内存的数据写入。可用策略会随 Redis 版本扩展，且 LRU/LFU 通常是采样近似；选择需结合访问分布、可重建性和持久数据语义

**缓存异常与一致性**

- **缓存穿透、击穿、雪崩有什么区别？** — 穿透是反复查询不存在的数据；击穿是热点 key 失效时并发回源；雪崩是大量 key 同时失效或缓存集群不可用。对应策略包括布隆过滤器或空值、单飞重建或逻辑过期、过期抖动与隔离降级
- **Cache Aside 如何工作？** — 读时先查缓存，未命中则读数据库并回填；写时通常先更新数据库再删除缓存。它只缩小不一致窗口，删除失败、并发读写和重试仍需业务按一致性目标处理
- **缓存一致性如何设计？** — 先定义可接受的不一致窗口和读写模型，再选择失效、更新、订阅变更日志或消息驱动同步。关键操作需要幂等、重试、补偿、监控和对账；不存在对所有业务都适用的单一固定顺序
- **过期与淘汰有什么区别？** — 过期是 key 到达 TTL 后失效，通常通过惰性删除与主动抽样清理；淘汰是在达到内存上限后按策略释放空间。策略要结合热点分布、可重建性和允许的写失败行为

**分布式锁边界**

- **Redis 锁的最低正确性要求是什么？** — 加锁使用带唯一 token 和过期时间的原子条件写；释放时原子校验 token 后删除；业务耗时超过租约时需要受控续约或失败退出
- **租约锁为什么不能自动保证业务正确？** — 进程停顿、网络分区、故障切换和超时后继续执行可能产生并发持有者。对不能容忍并发写的资源，应使用 fencing token、数据库约束或其他能拒绝过期持有者的机制

**多级缓存架构与选型**

- **本地缓存适合什么场景？** — 极高频、对微秒级读取敏感、数据量受控且允许短暂陈旧的数据。它减少跨进程访问，但让每个实例持有独立副本，增加失效广播、容量规划和一致性成本
- **本地缓存的内存成本如何表述？** — 本地缓存占用**当前进程内存**，不是天然只占 JVM 堆。Java 需区分堆内对象与 off-heap，并关注 GC 和对象开销；C++ 需关注所有权、分配器、碎片和 RSS；Go 需关注堆存活集、GC 频率、逃逸和 `GOMEMLIMIT`
- **Redis 适合什么场景？** — 多实例共享、容量较大、需要统一 TTL 或原子数据结构、需要独立扩缩容和高可用的缓存。真实延迟由网络拓扑、连接管理、请求大小、热 key 和服务端负载决定，不能写死为固定毫秒数
- **什么时候采用 L1 + L2？** — 只有 Redis 访问已被数据证明是瓶颈，热点集中且业务接受 L1 陈旧窗口时。典型链路是进程内 L1 → Redis L2 → 数据源；需同步设计版本、失效广播、回源保护、容量和降级

### 连续追问

1. 为什么需要缓存，当前数据库或下游的瓶颈证据是什么？
2. 这个命令在当前数据规模与 encoding 下复杂度是多少，会返回或复制多少数据？
3. 执行 `BGSAVE` 或 AOF rewrite 时，fork、COW、磁盘和容器内存的峰值如何观测？
4. Sentinel 故障转移或 Cluster 槽迁移期间，客户端发现、重试和数据一致性如何处理？
5. key 数量、value 大小、命中率、TTL、淘汰率和热点分布分别是多少？
6. 本地缓存占当前进程多少内存，Java/C++/Go 运行时下如何观测和限制？
7. 多实例如何失效，允许多久陈旧，消息丢失后如何修复？
8. Redis 故障、热 key 或缓存同时失效时，怎样保护数据源？
9. 如何通过压测和线上指标证明 L1 的收益超过复杂度，什么条件下删除 L1？

### 常见误区

- 把本地缓存统一描述为“占用 JVM 堆”，忽略其他语言和 off-heap 实现
- 把逻辑类型和内部 encoding 混为一谈，或把某个 Redis 版本的转换阈值当作永久规范
- 认为 RDB 只是“复制一份内存”，忽略 fork 延迟与写入触发的 COW 内存峰值
- 把 `everysec`、过期清理周期或 I/O threads 效果写成脱离环境的固定数值
- 认为 Sentinel 等同于分片，或认为 16384 slots 自动消除热点和复制丢失窗口
- 认为 LRU/LFU 一定维护精确全局顺序，不核对采样近似和目标版本策略
- 因“少一次网络请求”直接引入 L1，没有测量 Redis 延迟占端到端延迟的比例
- 认为先更新数据库再删缓存就实现强一致，不处理删除失败和并发窗口
- 把设置过期时间等同于可靠分布式锁，不考虑旧持有者继续写
- 缓存所有查询结果，却没有容量上限、key 基数评估和防缓存污染策略

## 3. 消息队列

### 基础问题与答案要点

- **为什么引入消息队列？** — 典型目标是异步解耦、削峰填谷、跨服务事件传播和失败隔离。引入后会增加端到端延迟、重复与乱序处理、积压治理和运维成本
- **如何选消息系统？** — 从吞吐、端到端延迟、消息模型、顺序范围、持久化与复制、消费语义、积压能力、生态和运维能力比较。Kafka、RocketMQ、RabbitMQ 等只是候选实现，不是标准答案
- **消息如何避免丢失？** — 生产端确认和重试，Broker 按业务目标持久化与复制，消费端在业务处理成功后提交进度；同时监控不可恢复错误和积压。任何环节都要明确失败窗口
- **如何处理重复消费？** — 常见交付语义是 at-least-once，消费者必须幂等。可使用业务唯一键、状态机条件更新、数据库唯一约束、去重表或幂等记录，不能只依赖内存标记
- **如何保证顺序？** — 先定义顺序作用域，通常只能保证同一分区或同一业务 key 的局部顺序；生产路由、Broker 存储和单 key 消费都要维持顺序。全局顺序会显著限制并发
- **重试与死信队列如何设计？** — 区分瞬时错误和永久错误，使用有限次数、退避和抖动；超过阈值进入死信或人工处理。重试必须保留原因、次数和原消息，并避免重试风暴
- **事务消息或 Outbox 解决什么问题？** — 解决数据库状态变更与消息发布的原子性缺口。Outbox 在本地事务写业务数据和事件表，再由独立发布器投递；仍需处理重复发布、清理和延迟

### 连续追问

1. 不使用消息队列时，业务目标是否能用同步调用或数据库任务更简单地完成？
2. 允许丢失、重复、乱序和延迟的边界分别是什么？
3. 生产成功但响应超时、消费成功但提交失败时会发生什么？
4. 消费者下游故障后积压增长速度、磁盘容量和恢复时间如何计算？
5. 扩分区或增加消费者时，局部顺序和重复处理如何变化？

### 常见误区

- 宣称“消息绝不丢失”或“exactly-once”而不说明作用范围、外部副作用和失败模型
- 用具体框架的默认配置代替业务可靠性设计
- 消费失败立即无限重试，导致故障放大并阻塞正常消息
- 为追求全局有序把吞吐压到单分区，却没有全局顺序的业务必要性
- 只监控消费成功率，不监控积压年龄、重试率、死信量和端到端延迟

## 4. 计算机网络

### 基础问题与答案要点

**TCP、HTTP 与 TLS**

- **TCP 三次握手解决什么问题？** — 双方交换并确认初始序列号，同时验证双向收发路径可用。两次握手无法让服务端确认客户端已收到服务端的序列号
- **TCP 四次挥手为什么通常是四次？** — TCP 是全双工，两个方向独立关闭；收到对方 FIN 后可先 ACK，待本方向数据发送完成再发 FIN。ACK 与 FIN 在条件满足时也可能合并
- **流量控制与拥塞控制有什么区别？** — 流量控制通过接收窗口保护接收端；拥塞控制根据网络反馈调整发送速率，避免路径过载。排查吞吐需区分应用、接收端和网络瓶颈
- **HTTP/1.1、HTTP/2、HTTP/3 的核心差异是什么？** — HTTP/1.1 常依赖多个连接缓解队头阻塞；HTTP/2 在单 TCP 连接上多路复用，但仍受 TCP 层丢包影响；HTTP/3 基于 QUIC，在传输层提供独立流并改进连接建立与迁移
- **TLS 提供什么保证？** — 通过证书链验证身份，协商密钥并提供传输机密性和完整性。TLS 1.3 减少握手往返，但证书验证、域名校验、时间和信任根仍是安全关键

**DNS、连接与 RPC**

- **DNS 解析链路有哪些缓存？** — 应用、操作系统、本地解析器和递归 DNS 都可能缓存；TTL、负缓存和连接复用会影响变更生效。故障排查要确认请求实际解析到的地址
- **长连接为何仍会失败？** — 空闲超时、NAT 或负载均衡回收、服务重启、半开连接和网络切换都可能中断。应用需要合理的连接超时、健康检查、重连和请求幂等
- **RPC 框架的核心职责是什么？** — 服务寻址、序列化、传输、超时、取消、重试、负载均衡、错误映射和可观测性。标准答案应基于协议与失败语义，不绑定单一语言框架
- **RPC 超时与重试如何设计？** — 超时预算从入口沿调用链递减并传递取消；只有可安全重放的操作才自动重试，使用有限次数、退避和抖动，并防止多层重试放大流量
- **序列化如何选？** — 比较兼容性、Schema 演进、编码大小、CPU 成本、调试性和多语言支持。不能只用单次 microbenchmark 决定线上协议

### 连续追问

1. 用户看到 2 秒延迟时，DNS、建连、TLS、服务端处理和响应传输各占多少？
2. 请求超时后服务端是否仍可能成功执行，客户端重试会产生什么副作用？
3. 四层与七层负载均衡分别能看到什么信息，健康检查失败如何影响连接？
4. 协议字段删除、重命名或类型变化时，如何保证新旧客户端兼容？
5. 网络分区和高延迟如何通过 trace、连接指标和抓包相互验证？

### 常见误区

- 把 HTTP 状态码、RPC 业务错误和传输失败混为一类
- 所有超时都自动重试，忽略非幂等写和重试风暴
- 只说“网络抖动”，没有 DNS、握手、重传、连接池或服务端证据
- 认为使用长连接就没有建连和连接回收问题
- 用某个 RPC 框架的 API 名称代替超时、取消、序列化和兼容性原理

## 5. 操作系统

### 基础问题与答案要点

- **进程与线程有什么区别？** — 进程提供资源和地址空间隔离，线程是进程内的执行与调度实体并共享大部分进程资源。具体调度和实现细节取决于操作系统与语言运行时
- **常见进程间通信方式有哪些？** — 管道、消息队列、共享内存、信号、Socket 和文件等。选型需比较复制成本、同步方式、跨机能力、权限边界和故障处理
- **虚拟内存解决什么问题？** — 为进程提供独立连续地址空间，通过页表映射物理内存或后备存储，实现隔离、按需分配和共享。缺页不一定意味着从磁盘换入，也可能是首次分配或文件映射
- **用户态与内核态切换为何有成本？** — 系统调用、异常或中断会进入内核处理，伴随上下文保存、权限切换和可能的调度；真实成本需测量，不能把所有性能问题归因于“上下文切换”
- **阻塞 I/O、非阻塞 I/O 与 I/O 多路复用如何区分？** — 阻塞描述调用等待行为；非阻塞调用立即返回状态；多路复用让一个执行线程等待多个描述符就绪。数据就绪后通常仍需实际读写
- **页面置换算法有哪些？** — FIFO、LRU、LFU、Clock 等体现不同的历史信息和实现成本；操作系统通常使用近似算法，而不是维护严格 LRU

**并发模型**

- **共享内存之外有哪些并发模型？** — Actor 通过隔离状态和异步消息协作；事件循环用少量执行线程处理大量 I/O 事件；消息队列跨进程解耦生产与消费。它们减少部分共享状态竞争，但仍需处理消息顺序、背压、失败和状态一致性
- **Lock-free 的含义是什么？** — 系统整体能在有限步骤内持续取得进展，即使个别执行线程暂停；常依赖原子读改写与重试。Lock-free 不等于 wait-free，也不等于无竞态或一定更快
- **何时选择消息传递而不是共享内存？** — 当状态天然可分区、组件需要故障隔离或跨进程扩展时，消息传递更易建立所有权边界；低延迟共享数据访问或需要多对象原子更新时，复制和协议成本可能更高
- **无锁方案如何验证？** — 除功能测试外，需检查内存顺序、ABA、资源回收、饥饿和高冲突下的重试成本，并使用目标语言的竞态检测、模型检查或压力测试工具补充证据

**通用死锁**

- **死锁的四个必要条件是什么？** — 互斥、持有并等待、不可剥夺、循环等待。这里描述语言无关的资源依赖关系，不绑定任何具体并发原语
- **如何预防或避免死锁？** — 统一资源申请顺序、一次性申请、允许超时和回退、缩小持有范围，或在资源分配前判断安全状态。不同策略会牺牲并发、吞吐或实现复杂度
- **如何检测死锁？** — 建立线程或事务对资源的持有与等待关系，检测 wait-for graph 中的环；采集多个时刻的阻塞栈、锁/事务信息和调度状态，区分死锁、活锁、饥饿和普通长等待

### 连续追问

1. 线程数增加后吞吐为什么可能下降，如何区分调度、锁和 I/O 等待？
2. RSS、虚拟内存、匿名页、文件页和语言运行时统计为什么可能不同？
3. 发生 major page fault 时对尾延迟有什么影响，如何从系统指标证明？
4. 一个服务看似“卡死”时，如何判断是死锁、活锁、资源耗尽还是下游等待？
5. 采用无锁结构后是否就没有并发问题，饥饿和重试开销如何评估？
6. Actor 或事件循环中没有传统互斥锁时，仍可能出现哪些逻辑死锁、邮箱积压或阻塞回调问题？

### 常见误区

- 把进程称为 CPU 调度的唯一单位，忽略现代系统主要调度线程或任务
- 把虚拟内存大直接等同于物理内存泄漏
- 看到高上下文切换次数就直接调小线程池，不分析工作负载和 runnable/blocked 状态
- 通用死锁回答只背某一种语言的锁实现和工具
- 认为异步 I/O 必然更快，忽略负载规模、批处理、复制和编程复杂度

## 6. 分布式系统

### 基础问题与答案要点

- **CAP 应该如何理解？** — 发生网络分区时，系统必须在保持一致性和继续对部分请求提供可用响应之间取舍。CAP 讨论的是分区条件下的行为，不是日常状态中任意“选两个”
- **BASE 表达什么思路？** — 通过基本可用、允许中间状态和最终一致性换取系统可用性与扩展性。最终一致必须定义收敛条件、最大延迟、冲突处理和异常修复
- **分布式一致性模型有哪些差异？** — 线性一致、顺序一致、因果一致、会话保证和最终一致对操作可见顺序承诺不同。业务应从不变量和用户体验选择，不应默认所有数据都要求最强一致
- **分布式锁如何选？** — 先判断是否能用数据库唯一约束、条件更新、分区归属或幂等消除锁。确需锁时明确租约、续期、故障模型和 fencing token；实现可以基于数据库、协调服务或缓存，但正确性不能只看吞吐
- **分布式 ID 有哪些方案？** — UUID 去中心化但较大且通常无序；数据库序列简单但有中心依赖；号段降低中心访问；Snowflake 类方案高吞吐、趋势递增，但需处理时间回拨、节点 ID 和位宽寿命
- **2PC、TCC、Saga 与 Outbox 如何取舍？** — 2PC 提供协调提交但阻塞和可用性成本高；TCC 需要业务预留、确认和取消；Saga 通过多个本地事务及补偿推进长事务；Outbox 解决本地状态与事件发布原子性。选择取决于一致性、不变量、参与者和补偿可行性
- **一致性哈希解决什么问题？** — 节点变化时只迁移部分 key；虚拟节点改善负载分布。它不自动解决热点、容量差异、副本一致性和故障恢复
- **熔断、隔离和降级分别是什么？** — 熔断在失败达到阈值后暂时拒绝调用；隔离限制故障影响的资源池或并发；降级牺牲非核心能力维持主链路。三者都需要恢复探测和可观测性

### 连续追问

1. 业务真正必须维护的不变量是什么，弱一致会造成什么可见后果？
2. 网络分区时哪些请求继续服务，哪些拒绝，客户端如何感知？
3. 协调者或参与者在每个阶段宕机后，状态如何恢复或人工修复？
4. 补偿操作失败、重复或顺序颠倒时，如何保证幂等并持续收敛？
5. 扩容、时钟回拨和跨地域延迟会怎样影响 ID、锁和数据复制？

### 常见误区

- 把 Redis 固定标为 AP、ZooKeeper 固定标为 CP 后就结束设计，不讨论具体操作和故障语义
- 将最终一致解释为“最终总会一致”，却没有重试上限、对账和人工修复
- 业务可用唯一约束解决，仍引入分布式锁并扩大故障面
- 补偿等同于数据库回滚，忽略外部副作用通常不可逆
- 使用 Snowflake 类 ID 却没有节点 ID 冲突和时钟回拨策略

## 7. 系统设计

### 基础问题与答案要点

**设计方法**

- **系统设计题如何开始？** — 先澄清功能范围、用户与流量规模、读写比例、数据量、延迟和一致性目标，再估算容量，画主链路和数据模型，最后讨论瓶颈、故障、观测与演进
- **水平扩展与垂直扩展如何选？** — 垂直扩展简单但受单机上限和故障域限制；水平扩展提升总容量和容错，但引入分片、协调和一致性成本。通常先消除低成本瓶颈，再按增长路径扩展
- **状态放在哪里？** — 服务进程尽量无状态便于扩缩容；会话、任务和业务状态进入有明确一致性与生命周期的存储。JWT 也不是“没有状态”，撤销、权限变更和密钥轮换仍需设计

**高频场景**

- **秒杀系统如何分层？** — 静态内容前置缓存；入口鉴权、限流和防重；库存用原子条件更新防超卖；请求异步化削峰；订单状态可查询；全链路设计幂等、补偿和对账
- **短链系统如何设计？** — ID 编码或哈希生成短码，处理碰撞与热点；存储长短映射并设置缓存；跳转码需根据永久性与缓存语义选择；同时考虑滥用检测、过期和统计
- **读写分离如何处理一致性？** — 读请求默认走副本，写后读可临时读主、携带版本水位或等待副本追平；策略取决于业务允许的陈旧窗口和主库容量
- **限流有哪些通用算法？** — 固定窗口简单但边界突刺；滑动窗口更平滑但状态成本高；漏桶平滑输出；令牌桶允许受控突发。实现位置可在客户端、网关、服务或共享存储，不应以单一语言库作为标准答案
- **限流阈值如何确定？** — 基于下游安全容量、SLO、并发模型和压测曲线，并预留故障余量。分布式场景需定义全局或实例级精度、时钟、状态一致性和故障降级

**容量与可靠性**

- **容量估算至少包含什么？** — 峰值和平均 QPS、并发数、请求与响应大小、数据增长、缓存命中、网络带宽、CPU/内存/磁盘、复制和备份成本
- **如何消除单点？** — 多实例、多可用区、副本和自动故障转移只是基础；还需验证控制面、配置、DNS、证书、依赖和发布系统是否仍是单点
- **如何设计降级？** — 明确核心与非核心链路，给非核心功能设置超时、缓存或默认结果；降级必须可观测、可恢复，并避免返回看似成功但违反业务约束的数据

### 连续追问

1. 估算中的峰值系数和增长假设来自哪里，最敏感的变量是什么？
2. 单个依赖变慢而非完全宕机时，线程、连接和队列如何耗尽？
3. 限流拒绝哪些请求，客户端重试是否会进一步放大流量？
4. 缓存、数据库和消息系统各自失效时，核心业务还能维持到什么程度？
5. 从单地域演进到多地域时，一致性、路由、数据主权和成本如何变化？

### 常见误区

- 未澄清规模就堆叠缓存、分库分表和消息队列
- 只画正常链路，不说明超时、重试、幂等、降级、恢复和数据修复
- 限流算法背得完整，却没有阈值来源、作用范围和拒绝后的客户端行为
- 用具体框架组件名称代替协议、数据流和故障模型
- 把“无状态服务”理解为整个系统无状态

## 8. 性能分析与故障排查

### 基础问题与答案要点

- **性能优化的第一步是什么？** — 明确用户可见目标和基线，例如吞吐、p50/p95/p99 延迟、错误率、资源成本和数据规模；先复现和定位瓶颈，再提出假设，不从工具或参数开始
- **USE 与 RED 方法分别看什么？** — USE 对每种资源看利用率、饱和度和错误；RED 对每个服务看请求速率、错误和持续时间。二者结合可从服务症状下钻到资源原因
- **CPU 高如何分析？** — 确认配额和负载变化，区分 user/system/iowait/steal，定位进程与执行线程，再用采样 profiler、调用栈和业务指标验证热点
- **内存问题如何分析？** — 区分语言堆、原生内存、文件页、映射、线程栈和内核资源；观察分配速率、回收后存活集、RSS 与 OOM 事件，必要时分析 heap/core dump
- **I/O 与数据库慢如何分析？** — 查看队列深度、吞吐、延迟、IOPS 和饱和度，并关联查询、锁等待、缓存命中和网络。高磁盘利用率本身不是根因
- **线上故障的证据链是什么？** — 时间线、用户症状、变更记录、指标、日志、trace、profile/dump 和依赖状态应互相印证。先止损再定位，所有高开销诊断先评估生产风险
- **优化如何验证？** — 在可比流量和数据下做 baseline、单变量实验和压力测试，检查收益、错误率和资源成本；通过灰度发布验证线上效果，并提前定义回滚阈值

### 连续追问

1. 当前结论能解释哪些指标，哪些指标与它矛盾？
2. 如果移除最近变更仍未恢复，下一条可证伪假设是什么？
3. profiling、抓包或 dump 的开销与安全边界是什么？
4. 平均延迟下降但 p99 和错误率上升，是否算优化成功？
5. 故障恢复后如何补齐监控、演练、容量和自动化防线？

### 常见误区

- 看到 CPU 或内存高就扩容，没有证明它与用户症状存在因果关系
- 只看平均值，掩盖尾延迟、热点实例和少量严重错误
- 先修改线程数、GC、连接池或超时，再寻找基线
- 把相关性当因果，忽略同一时间的发布、流量和下游变化
- 只口头说“压测有效”，不记录数据集、环境、命令、指标和对照结果

## 9. 工程实践

### 基础问题与答案要点

- **API 设计的基本要求是什么？** — 资源和动作语义清晰，输入输出有 Schema，错误模型稳定，鉴权与幂等明确，分页和批量边界受控，并有兼容演进规则
- **幂等如何实现？** — 读取天然幂等；写操作可使用幂等键、唯一约束、条件更新或状态机。必须定义幂等记录的作用域、TTL、并发竞争和响应重放
- **测试如何分层？** — 单元测试验证纯逻辑和边界；集成测试验证数据库、消息、缓存和外部协议；契约测试保护服务接口；少量端到端测试覆盖关键用户路径
- **数据库变更如何安全发布？** — 使用向后兼容的 expand-and-contract：先增加新结构并双读/双写或回填，再切流，最后移除旧结构；大表 DDL 需评估锁、复制延迟和回滚
- **配置与密钥如何管理？** — 配置与制品分离；敏感值进入密钥系统，不进入代码、日志或仓库；配置有类型校验、审计、灰度和回滚
- **可观测性应覆盖什么？** — 指标回答“是否异常”，日志提供离散事件上下文，trace 展示跨服务因果路径；统一 request/trace ID，并控制敏感信息、采样和基数
- **发布策略如何选？** — 滚动发布成本低；蓝绿便于快速切换但资源成本高；金丝雀先验证小流量。无论哪种都需兼容新旧版本并定义自动停止与回滚指标
- **代码审查关注什么？** — 正确性、边界、失败语义、安全、并发、数据迁移、可观测性和测试证据优先于格式；审查结论应能指向代码、协议或运行证据

### 连续追问

1. 客户端超时重试时，写接口如何避免重复副作用？
2. 新旧服务版本同时运行时，API、消息和数据库 Schema 如何兼容？
3. 单元测试通过后，哪些真实边界仍必须通过集成或契约测试验证？
4. 灰度期间哪些指标触发自动停止，数据已经写入后如何回滚？
5. 日志与 trace 如何既支持排障，又避免泄露凭据和用户隐私？

### 常见误区

- 把 HTTP `PUT` 或 `POST` 方法本身当作幂等保证
- 测试数量很多但都 mock 掉数据库、事务和消息边界
- 先删除旧字段再升级所有消费者，造成不可逆兼容故障
- 只记录字符串日志，没有稳定字段、关联 ID、级别和采样策略
- 发布成功只看进程存活，不看业务错误、延迟、数据一致性和用户指标
